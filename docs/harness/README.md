# Harness 系统 - AI 开发基础设施

> Harness 是一套工程基础设施,给 AI 套上"缰绳",确保开发过程可控、不犯错。

---

## 📋 系统概述

### 什么是 Harness?

Harness 是一套约束和指导 AI 助手的基础设施,解决"**怎么不出错**"的问题。

### 核心问题

AI 开发过程中的三大挑战:

1. **过早宣布胜利**: 说 Done 但代码跑不通
2. **上下文焦虑**: 长任务赶进度,跳过验证
3. **跨会话失忆**: 新会话忘了旧约定

### Harness 的解决方案

| 子系统 | 解决问题 | 核心文件 |
|--------|---------|---------|
| **指令子系统** | AI 不知道该做什么、不该做什么 | `AGENTS.md` |
| **工具子系统** | AI 调用危险命令 | `docs/harness/TOOLS.md` |
| **环境子系统** | 环境不一致导致的问题 | `docs/harness/ENVIRONMENT.md` |
| **状态子系统** | 跨会话失忆 | `PROGRESS.md` |
| **反馈子系统** | 不验证就宣布完成 | `scripts/harness/validate_changes.py` |

## 📦 子系统详细说明

### 1. 指令子系统 (AGENTS.md)

**作用**: 告诉 AI 项目约定和规则

**核心内容**:
- 🚫 禁止操作 (文件系统、数据库、代码、命令)
- ✅ 必须遵守 (代码修改、测试、文档、Docker)
- 🔧 工具调用限制
- 📊 任务完成标准
- 🐛 错误处理规则

**位置**: `AGENTS.md` (项目根目录)

**示例规则**:
```markdown
❌ 禁止删除任何 .md 文档
✅ 修改任何代码前,必须先说明修改原因和影响范围
✅ 任何功能修改后,必须运行相关测试
```

---

### 2. 工具子系统 (TOOLS.md)

**作用**: 限定 AI 能调用哪些命令,禁止危险操作

**核心内容**:
- ✅ 允许的工具和命令 (Docker、Git、Python、数据库)
- 🚫 禁止的命令 (rm -rf、git push --force、drop database)
- 🔧 工具使用最佳实践
- 🔐 安全限制 (API Key 保护、文件权限、数据保护)

**位置**: `docs/harness/TOOLS.md`

**示例限制**:
```bash
# ✅ 允许
docker compose up -d
git commit -m "fix: 修复 bug"
pytest tests/test_api.py -v

# ❌ 禁止
rm -rf /
docker system prune -a
git push --force
```

---

### 3. 环境子系统 (ENVIRONMENT.md)

**作用**: 锁定依赖版本,确保环境一致

**核心内容**:
- 🐍 Python 依赖版本锁定
- 🟢 Node.js 依赖版本锁定
- 🐳 Docker 镜像版本
- 🔧 开发工具版本要求
- 📦 环境初始化流程
- 🔒 版本升级策略

**位置**: `docs/harness/ENVIRONMENT.md`

**版本锁定文件**:
```
requirements-lock.txt  - Python 完整依赖锁定
frontend/yarn.lock     - Node 依赖锁定
.python-version        - Python 版本锁定
```

---

### 4. 状态子系统 (PROGRESS.md)

**作用**: 跨会话持久化进度

**核心内容**:
- 📊 当前状态概览
- ✅ 已完成任务
- 🔄 进行中任务
- 📋 待办任务
- 🐛 已知问题
- 💡 重要决策记录
- 📚 参考资料

**位置**: `PROGRESS.md` (项目根目录)

**更新规则**:
```markdown
每次会话结束前必须更新:

## [日期] 会话进度

### 已完成
- [x] 任务 1: 描述

### 进行中
- [ ] 任务 2: 描述 (进度 50%)

### 已知问题
- 问题 1: 描述 + 临时解决方案
```

---

### 5. 反馈子系统 (validate_changes.py)

**作用**: 强制跑测试、lint、类型检查,退出码不为 0 不算完成

**核心检查**:
1. ✅ Python 语法检查 (py_compile)
2. ✅ Docker Compose 配置验证
3. ✅ Docker 服务状态检查
4. ✅ API 健康检查
5. ✅ 依赖完整性检查
6. ✅ 环境配置文件检查
7. ✅ 项目结构检查

**位置**: `scripts/harness/validate_changes.py`

**使用方法**:
```bash
# 运行验证
python scripts/harness/validate_changes.py

# 检查退出码
echo $?  # 0 = 全部通过, 1 = 有失败
```

**输出示例**:
```
============================================================
Harness 反馈验证系统
============================================================

✅ Python 语法检查: 通过 (245/245 文件)
✅ Docker Compose 配置检查: 通过 (4 个服务)
✅ Docker 服务状态检查: 通过 (4/4 运行)
✅ API 健康检查: 通过
✅ 依赖完整性检查: 通过
✅ 环境配置文件检查: 通过
✅ 项目结构检查: 通过

总计: 7/7 通过

🎉 所有检查通过! 代码可以提交。
```

## 🚀 使用流程

### 开发前

1. **阅读 AGENTS.md** - 了解项目规则
2. **检查 PROGRESS.md** - 了解当前进度
3. **验证环境** - 运行 `validate_changes.py`

```bash
# 验证环境
python scripts/harness/validate_changes.py
```

### 开发中

1. **遵循 AGENTS.md 规则**
2. **使用允许的工具和命令**
3. **记录进度到 PROGRESS.md**

### 开发后

1. **运行验证脚本**
   ```bash
   python scripts/harness/validate_changes.py
   ```

2. **检查退出码**
   ```bash
   echo $?  # 必须是 0
   ```

3. **更新 PROGRESS.md**
   ```markdown
   ## [日期] 会话进度
   
   ### 已完成
   - [x] 任务描述
   ```

4. **提交代码**
   ```bash
   git add .
   git commit -m "feat: 添加新功能"
   ```

## 🎯 失败模式预防

### 1. 过早宣布胜利

**症状**:
```
AI: "任务完成!"
实际: 代码跑不通,测试失败
```

**预防**:
```
✅ 反馈子系统强制验证
✅ 退出码不为 0 不算完成
✅ 必须提供验证证据 (测试输出、curl 结果)
```

### 2. 上下文焦虑

**症状**:
```
AI: 长任务赶进度,跳过验证步骤
```

**预防**:
```
✅ AGENTS.md 规定必须逐步验证
✅ PROGRESS.md 记录每个步骤的状态
✅ 工具子系统限制跳过验证的命令
```

### 3. 跨会话失忆

**症状**:
```
新会话: 忘记之前的决策和约定
```

**预防**:
```
✅ PROGRESS.md 持久化所有决策和进度
✅ AGENTS.md 记录所有项目规则
✅ 每次会话开始前必须阅读这两个文件
```

**时机**:

```

```

## 🎓 最佳实践

### 1. 渐进式采用

不要一次性引入所有规则,逐步添加:

```
第 1 周: AGENTS.md + 基本规则
第 2 周: PROGRESS.md + 状态跟踪
第 3 周: 验证脚本 + 自动化检查
第 4 周: 工具子系统 + 安全限制
```

### 2. 规则可执行

规则必须可验证,不是口号:

```
❌ 错误: "代码要高质量"
✅ 正确: "所有 Python 文件必须通过 py_compile 检查"
```

### 3. 持续改进

定期回顾和更新规则:

```
每周回顾:
- 哪些规则有效?
- 哪些规则需要调整?
- 有没有遗漏的规则?
```
